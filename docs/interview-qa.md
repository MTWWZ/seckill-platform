## 0. 一分钟项目介绍（背熟）

> 这是一个限时抢购（秒杀）交易系统，后端 Spring Boot，配了 Vue3 管理后台和 uni-app 用户端。
> 核心解决的是**高并发下的不超卖和异步下单**：库存扣减放在 Redis 用 Lua 原子完成，配合数据库唯一索引和条件更新做四道防线；订单落库交给 RabbitMQ 异步削峰；未支付订单用 TTL + 死信延迟队列自动取消并回补库存。
> 工程化上补齐了 JUnit5 测试、GitHub Actions CI、Flyway 迁移、Docker Compose 和 Prometheus/Grafana 监控。
> 实测 50 个用户并发抢 10 件库存，恰好 10 单成功、零超卖；200 并发下单 QPS 约 245。

## A. 项目整体（4 题）

### A1 ⭐ 为什么做这个项目？
想完整走一遍「高并发写链路」：从空库到能演示、能压测、能监控。秒杀这个场景自带超卖、幂等、削峰、超时这些必须正面解决的问题，比增删改查更能体现设计能力。

### A2 项目里你负责哪部分？
三端都是自己写的：后端 20 个接口、管理后台、用户端小程序，以及测试、CI、容器化和文档。

### A3 整体架构是什么样？
用户端和管理后台都走 HTTP 打到 Spring Boot；后端读 MySQL、写 Redis、收发 RabbitMQ；Prometheus 抓 Actuator 指标给 Grafana 展示。写路径不碰数据库——先扣 Redis，再发 MQ，消费者异步落库。

### A4 最大的难点是什么？
不是某个 API，而是**让「扣库存」「落库」「关单」三件事在失败场景下仍然对得上账**。所以设计了补偿：MQ 投递失败同步回滚、消费失败进死信、超时关单幂等回补、定时任务兜底。

## B. 秒杀与并发（12 题）

### B1 ⭐ 怎么防止超卖？
四道防线：
1. Redis Lua 脚本把「判断库存 + 扣减 + 记录用户」合成一次原子操作；
2. Redis Set 做一人一单；
3. 数据库唯一索引 `uk_user_activity` 兜底；
4. 状态流转用 `UPDATE ... WHERE status = 0` 条件更新。
最终以「成功数 = 库存数」验证：50 并发抢 10 件，恰好 10 单。

### B2 ⭐ 为什么库存扣减放 Redis，不直接扣数据库？
数据库行锁在瞬时几百并发下会大量排队，响应时间飙升；Redis 是单线程内存操作，Lua 内完成判断和扣减，吞吐高一个量级。数据库只承担「可靠落库」，不参与并发决策。

### B3 ⭐ Lua 为什么能保证原子性？
Redis 执行 Lua 时是单线程且不可中断，脚本内部不会有其它命令插进来。如果拆成 `GET` 再 `DECR`，多个请求可能读到同一库存值，扣成负数。

### B4 ⭐ 一人一单怎么做的？
Lua 里先 `SISMEMBER` 用户集合，已存在直接返回 2；否则 `SADD` + `DECR`。数据库层再用唯一索引兜底，防止消息重复投递或应用层判断失效。

### B5 ⭐ 为什么不用分布式锁（Redisson）？
锁会把并发串行化，而且多一次加锁/解锁的网络往返；Lua 在一个 RTT 内完成「查 + 改」，天然互斥，吞吐更高。锁更适合「必须串行访问共享资源」的场景，这里用不上。

### B6 🔥 Redis 扣成功了，但消息发不出去怎么办？
发送异常时同步补偿：`INCR` 库存、`SREM` 用户标记，然后返回 500。如果不回滚，就会出现「扣了库存却没有订单」的少卖。

### B7 🔥 消息重复消费怎么办？
两道幂等：消费前先按 `user_id + activity_id` 查一次；插入时用唯一索引兜底，捕 `DuplicateKeyException` 也当作成功 ACK。

### B8 🔥 消息丢了怎么办？
三层：生产者发送失败同步回滚；消费者失败 `nack(requeue=false)` 进死信队列，可人工重放；超时关单另有每分钟一次的定时补偿任务。

### B9 削峰是怎么实现的？
接口只做「扣 Redis + 发消息」就返回，不写数据库；MQ 把峰值堆住，消费者按 `prefetch=20` 的节奏落库。请求耗时从「等 insert」降为「一次 Redis + 一次 publish」。

### B10 库存回补会不会重复加？
不会。取消条件是 `UPDATE ... WHERE id=? AND status=0`，只有影响行数为 1 的那一次才去 `INCR`。延迟消息和定时任务同时盯上同一单，也只会回补一次。

### B11 ⭐ 未支付订单超时怎么实现？为什么不用定时扫表？
主路径是 RabbitMQ 延迟队列：下单后投一条 15 分钟 TTL 的消息，到期死信到超时队列，消费者回查订单状态决定是否取消。延迟队列到点触发、精度高、不压数据库；定时任务每分钟扫一次只做兜底。

### B12 🔥 延迟队列的 TTL 有什么坑？
RabbitMQ 的队列级 TTL 是队列统一的，消息会**队头阻塞**——如果一条消息 TTL 很长，后面的短 TTL 消息也得等它过期。本项目固定 15 分钟，没有这个问题；如果要支持不同延迟，得用每消息 TTL + 死信，或用延迟插件/时间轮。

## C. Redis 与缓存（6 题）

### C1 ⭐ 缓存一致性怎么保证？
Cache-Aside：读未命中查库回写；写操作**删除缓存**而不是更新缓存——并发下更新缓存可能写入旧值，删除最多让下一次读回源。

### C2 🔥 为什么不做延迟双删？
延迟双删是为了解决「删缓存后、数据库主从延迟导致旧值又被读回缓存」的问题。当前是单库、无主从延迟，收益不大；如果上主从，会补这一步。

### C3 缓存穿透、击穿、雪崩分别怎么处理？
- 穿透：不存在的商品缓存 `__EMPTY__` 占位，TTL 1 分钟；
- 击穿：热点 key 失效瞬间打库，可用互斥锁/逻辑过期，当前商品详情访问量不大，没做；
- 雪崩：TTL 加随机抖动（基础 30 分钟 + 300 秒），避免同一批 key 同时失效。

### C4 🔥 秒杀库存 key 为什么不设 TTL？
库存是业务状态，不是缓存。设了 TTL 到期就「凭空回满库存」，直接超卖。宁愿占这点内存。

### C5 🔥 预热任务会不会把进行中的库存刷回初始值？
不会。预热前先 `hasKey` 判断，已存在就跳过；只有 key 不存在（活动还没开始或刚重建）才写入。

### C6 Redis 单线程为什么快？
纯内存操作、避免了多线程锁竞争和上下文切换、用 IO 多路复用处理连接。6.0 之后网络 IO 可以多线程，但命令执行仍是单线程。

## D. 消息队列（5 题）

### D1 ⭐ 为什么用 RabbitMQ，不用 Kafka？
RabbitMQ 的路由、死信、延迟能力开箱即用，适合「业务消息 + 延迟关单」；Kafka 更强在日志型高吞吐与回放，本项目的量级用不到。选型看场景，不是看谁更火。

### D2 交换机为什么用 direct？
每种消息目的明确（下单、延迟、超时），direct 按 routing key 精确投递就够了；topic 适合模糊匹配，这里没必要。

### D3 手动 ACK 和自动 ACK 的区别？
自动 ACK 在消息投递时就确认，消费者处理失败会丢消息；手动 ACK 在业务成功后确认，失败可以 nack 进死信。我们全程手动 ACK。

### D4 🔥 消息积压了怎么处理？
先看是消费慢还是生产突增：消费者可以扩实例（同一队列竞争消费）；也可以临时提高 prefetch 提升吞吐；极端情况把消息转存到新队列再慢慢消费。监控里 `seckill_queue_messages` 就是看这个。

### D5 消息需要保证顺序吗？
不需要。每笔订单用唯一索引保证幂等，订单之间没有先后依赖。

## E. 数据库与事务（4 题）

### E1 为什么扣库存不在数据库事务里做？
秒杀写路径根本不碰数据库；事务只包裹「单条订单插入」这种简单操作。把并发决策放进事务会放大锁竞争。

### E2 索引怎么设计的？
- `uk_user_activity`：一人一单的最终防线；
- `uk_order_no`：订单号唯一；
- `idx_status_create (status, create_time)`：超时补偿任务按状态 + 时间扫描；
- `idx_activity_id`：按活动查订单。

### E3 `seckill_activity` 里的 version 字段用了吗？
预留给乐观锁，实际没用到——并发控制放在了 Redis Lua 层，数据库不做版本竞争。这是可以坦白说的「预留字段」。

### E4 金额为什么用 BigDecimal？
double 有精度误差（0.1 + 0.2 ≠ 0.3），金额必须精确；并且数据库用 `DECIMAL(10,2)` 对应。

## F. 鉴权与安全（4 题）

### F1 ⭐ JWT 的优缺点？
优点：无状态、服务端不存 session、天然适合多端。缺点：签发后无法主动失效、载荷不能放敏感信息、续期要额外设计。当前 token 有效期 2 小时，没有 refresh 和黑名单，是已知不足。

### F2 🔥 401 和 403 的区别？
401 = 没登录或 token 失效（认证失败）；403 = 登录了但权限不够（授权失败）。项目里 `/api/admin/**` 由单独的拦截器校验 `role=1`，普通用户返回 403。

### F3 密码为什么用 BCrypt？
自带盐、计算慢，能抵抗彩虹表和暴力破解；MD5/SHA 太快且无盐，不适合存密码。

### F4 ⭐ 限流怎么实现的？固定窗口有什么问题？
注解 + AOP + Redis Lua：`SET key 1 EX window` 计数，超过阈值抛 429。支持 USER / IP / GLOBAL 三个维度。
固定窗口的问题是**临界突刺**：窗口边界前后各打满一次，实际可能短时间翻倍。更严谨可以用滑动窗口或令牌桶，本项目接口量级下固定窗口够用。

## G. 工程化与运维（5 题）

### G1 ⭐ 测试怎么保证不影响开发数据？
独立 `seckill_test` 库 + Redis 15 号库；每个用例前清订单、活动与测试 Redis；Rabbit 监听器 `auto-startup=false`，`RabbitTemplate` 用 `@MockitoBean` 替换，测试消息不会进开发队列。

### G2 13 个用例覆盖了什么？
并发不超卖、一人一单、限流 429 分布、鉴权 401、权限 403/200、支付幂等、他人订单 404、超时关单只回补一次、已支付不被取消、已取消不能支付。

### G3 ⭐ Flyway 怎么接入已有库的？
`baseline-on-migrate=true` + `baseline-version=0`：已有表但没有版本记录时先基线到 0，再执行 V1；V1 用 `CREATE TABLE IF NOT EXISTS` 保证对存量库幂等。空库则完整建表。

### G4 Docker Compose 的端口为什么这样设计？
MySQL / Redis / AMQP 不映射宿主机端口，容器间用服务名互访，避免和本机已跑的 3306/6379/5672 冲突；只暴露 8080 后端、8081 后台、15672 MQ 台、9090/3000 监控。

### G5 监控都看什么？
Actuator 自带 HTTP/JVM/连接池指标；另外加了三个业务指标：抢购结果计数 `seckill_order_result_total{result}`、活动库存 `seckill_activity_stock`、队列积压 `seckill_queue_messages`。Grafana 12 块面板。
注意点：Micrometer 默认只输出 summary，必须打开 `percentiles-histogram` 才有 `_bucket`，否则 P95 算不出来。

## H. 压测与性能（3 题）

### H1 ⭐ 怎么压测的？
零依赖 Node 脚本 `scripts/loadtest.mjs`：先批量注册临时账号（保证不同用户），再一次性并发下单，统计业务码、QPS、P50/P95/P99。
结果：50 并发抢 10 件 → 10 成功 + 40 个 400，334ms，QPS 149.7；200 并发抢 200 件 → 全部成功，816ms，QPS 245.1，P95 746ms。

### H2 🔥 QPS 245 算高吗？瓶颈在哪？
不算高，瓶颈不在 Redis，而在每个请求都要做一次活动查询 + 一次 MQ 发布，且是单机、单消费者、连接池有限。提升方向：活动信息本地缓存、批量/异步确认、消费者多实例、连接池调优、水平扩容。

### H3 怎么证明数据对得上？
压测后直接对账：Redis 库存归 0，数据库订单数 10 / 200，与成功数一致，没有负数。这比只看「没报错」更有说服力。

## I. 开放题（3 题）

### I1 项目有什么不足？
支付是模拟实现；小程序端只验证了构建；Docker Compose 未实际拉起；商品/活动 CRUD 没有测试；JWT 没有刷新与登出失效；定时任务单机部署需要分布式锁。

### I2 如果重做，会优先改什么？
先把支付回调闭环和支付渠道接上；再加链路追踪（traceId 贯穿下单全流程）；最后补商品 CRUD 与缓存一致性的测试。

### I3 遇到过最难查的问题？
用户端活动详情页会让 H5 渲染进程卡死。按区块二分重建才定位到是整页组合的问题，不是某个组件。教训是：先缩小范围，再怀疑具体代码。

## 答题建议

1. **用数字结尾**：每条关键回答尽量带一个实测数字（10 单、245 QPS、13 个用例）。
2. **先说结论，再说原因**：面试官没耐心听铺垫。
3. **主动交底**：「这块我没做」比编一个方案更安全，接着补一句「我会怎么做」。
4. **被追问到底层不会时**：承认边界，把话题拉回你熟的链路，比如「这块我了解得不深，但这个项目的库存一致性我是这样保证的……」。
